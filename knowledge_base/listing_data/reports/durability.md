# 故障、并发和持久目录

这些结果来自 2026-11-07 在本机用强制结束进程跑出来的测试，不是把服务正常关掉再打开。

线程里的锁只挡住同一个进程。跨进程靠 SQLite 的立即事务和检查点库自己的锁。PostgreSQL 没有上，因为现在还是单机。

## 故障窗口

| 步骤 | 期望 | 实际 |
| --- | --- | --- |
| 草稿已经停在确认，进程被强制结束后再打开 | 仍是等待确认，台账里 0 条写入；接着确认一次变成已写入，再确认不会写第二次 | 通过。状态保持 awaiting_confirmation，写入条数 0，然后 1 |
| 确认已经写入之后，进程被强制结束再打开 | 仍是已写入，写入条数仍是 1，不能再确认出第二条 | 通过 |
| SQLite 检查点还没写入时进程直接退出 | 任务停在 running，没有 Listing 被写出去 | 通过。退出码 86 |
| 文件快照还没保存时进程直接退出，再用文件模式打开 | 台账虽已是等待确认，但没有可恢复的检查点，确认被拒绝，写入条数 0 | 通过 |

文件快照仍可用 `LISTING_CHECKPOINT=file` 做单机演示。默认是 LangGraph 的 SqliteSaver。

## 并发

| 步骤 | 期望 | 实际 |
| --- | --- | --- |
| 两个进程同时确认同一任务 | 台账里只有 1 条写入 | 通过 |
| 一个进程改草稿，另一个进程用旧版本确认 | 写入最多 1 条 | 通过，写入条数不超过 1 |
| 两个用户同时各开一个任务 | 彼此看不到对方的任务 | 通过，打开对方任务会拒绝 |

## 推送和取消

| 步骤 | 期望 | 实际 |
| --- | --- | --- |
| 确认商品这一步先落盘，整次请求还没返回 | 事件表里已经能看到 resolve_product | 通过 |
| 推送循环收到断开 | 循环在 3 秒内结束，任务仍停在等待确认，不会被当成取消 | 通过。没有用 TestClient.stream：任务停在确认时它经常不送断开信号，while True 会挂住，GitHub 的测试任务也会被拖死。核对的是页面同一段 iter_listing_events |
| 再调用取消 | 状态变成已取消，事件里有取消，之后不能确认写入 | 通过 |

断开推送和取消任务是两件事。
